3. 基于两份分析结果，先综合结论，再决定是否进入执行阶段

分析要求：
1. 两个分析代理都必须基于证据独立判断，不能只重复彼此结论
2. 根因判断时，优先排查并明确区分以下高概率原因：
   - 项目提示词问题：例如提示词缺失、约束冲突、指令歧义、示例误导、上下文注入不完整
   - 代码问题：例如业务逻辑错误、边界条件遗漏、接口契约不一致、异常处理缺失
   - 需求文档问题：例如需求定义错误、约束遗漏、验收口径不一致、前后描述冲突
   - 技术文档问题：例如接口说明错误、字段语义错误、流程说明失真、依赖关系描述不完整
   - cases 产物问题：例如生成的 case 步骤错误、前置条件错误、断言错误、测试数据不合理
3. 如果发现问题更像来源于需求文档、技术文档或 cases 产物，不仅要指出表层问题，还要继续追溯对应的上游生成提示词，并判断是否需要修复该生成提示词
4. 如果更像环境、工具链或测试资产问题，不要硬归类为代码 bug，也不要强行修复
5. 分析时至少覆盖这些证据：
   - `oms_test/ai-e2e/cases/<case_name>/execution_result.json`
   - `oms_test/ai-e2e/cases/<case_name>/test_report.md`

   - `oms_test/ai-e2e/cases/<case_name>/attempt_*_failure_summary.md`

   - `oms_test/ai-e2e/cases/<case_name>/attempt_*_ai_result.json`
   - `runs/<session_name>/cursor_agent_logs/*.log`
   - 相关源码
   - 相关需求文档（位于`runs/<session_name>/`）、技术文档（位于`runs/<session_name>/`）、case 生成产物与其相关生成提示词
6. 可以使用 skill 中的辅助脚本先汇总失败 case；如果传了 cases，要带上 case 过滤参数
7. 结论必须有证据支撑，不能只复述测试报告
8. 如果证据不足，请明确说明缺口

执行要求：
1. 综合结论后，如果明确属于项目提示词问题、代码问题、需求文档问题、技术文档问题或 cases 产物问题，可以修改对应提示词、代码、文档、case 生成提示词或必要配置
2. 对于暂时无法明确归因的问题，可以尝试做最小范围的探测性修改，以缩小问题范围并验证假设，但最多只允许重试三轮
3. 每一轮探测性修改都必须记录：修改假设、涉及位置、预期缩小的范围、实际观察结果，以及为什么继续或停止重试
4. 一旦明确收敛，应执行最小必要正式修复，不要持续试错
5. 只要本轮执行阶段产生了任何实际改动，不论改动的是代码、提示词、文档、case 生成提示词还是必要配置，都必须按以下顺序尝试执行验证：编译或构建、热更到可验证环境、重新执行对应失败 cases、汇总验证结果

8. 如果无法热更、无法重跑对应 cases，必须明确说明阻塞原因、替代验证方式与剩余验证缺口；不能因为“本次只改了提示词/文档/配置而不是代码”就跳过 case 重跑要求
